# stream-status v0

Draft, November 2026. MIT licensed.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in
RFC 2119 and RFC 8174.

## 1. What it's for

A **sender** is any part of a live-video chain that can see a problem: an
encoder box, a phone app, a receiver, a relay, a hub. A **reader** is any app
that shows or acts on it: the box's own screen, a remote or companion app, a
hub dashboard, a scene switcher, a support tool.

The sender publishes **snapshots**. Each snapshot is the complete current list
of **findings** (what is wrong, or was wrong a moment ago), plus a **checked**
list (which parts it looked at, and which parts it can't see). The format says
nothing about the channel: a WebSocket message, an HTTP response, a file and a
message queue can all carry it. A compact in-band form for video is described
separately in [in-band-v0.md](in-band-v0.md).

Out of scope for v0: commands, acknowledging or dismissing, history queries,
raw statistics, authentication and transport security (those belong to the
channel that carries the snapshot).

## 2. Snapshot

A snapshot is a JSON object (RFC 8259, UTF-8).

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `format` | yes | `"stream-status"` | Identifies the format |
| `v` | yes | integer, `0` | Major version |
| `source` | yes | object | Who sent it (2.1) |
| `generated` | yes | RFC 3339 date-time | When the sender built this snapshot, on the sender's clock |
| `valid_for_ms` | yes | integer, 1000–600000 | How long a reader may treat this snapshot as current after receiving it |
| `live` | yes | object | The stream as a whole (2.2) |
| `findings` | yes | array, at most 64 | Findings (section 3); empty when nothing is wrong |
| `checked` | yes | array, at most 64 | What was checked (2.3); MAY be empty |
| `session_id` | no | string, 1–64 | **Draft hook, not specified yet.** An identifier shared by every part of one stream, so a reader can join snapshots from several senders. Its rules come in a later draft. Senders MAY set it; readers MUST NOT rely on it in v0 |

A sender MUST publish a new snapshot whenever its content changes, and
SHOULD publish one at least every 5 seconds even when nothing changes.
`valid_for_ms` SHOULD be at least twice the sender's longest interval plus
2 seconds; the recommended value with a 5-second interval is 12000.

### 2.1 `source`

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Stable identifier of the sender, 4–64 characters `[A-Za-z0-9_-]`. MUST NOT be a serial number, IMEI, MAC address, account name or anything else that identifies a person or device outside this format. A random value chosen at install time is the intended use |
| `boot` | yes | 1–64 characters, new on every restart of the sender's process |
| `seq` | yes | Integer ≥ 0, increased by one for every snapshot within a `boot` |
| `software` | no | Free label such as `name/1.2.3`, at most 64 characters |

### 2.2 `live`

| Field | Required | Values |
| --- | --- | --- |
| `state` | yes | `live` (the stream is reaching the receiver), `not_live` (no stream is running), `unknown` |
| `since` | yes | RFC 3339 date-time of the last change of `state`, or `null` when unknown |

`live` describes delivery, not content. A stream showing a standby picture,
a privacy cover or a BRB scene is still `live`. Readers SHOULD say so in those
words and SHOULD NOT imply the stream has stopped.

### 2.3 `checked`

Each entry is `{ "subject": …, "state": …, "as_of": … }`:

- `subject`: as in 3.1.
- `state`: `fine` (checked, nothing wrong), `finding` (see the findings list),
  `unknown` (the sender has no current data about this part).
- `as_of`: date-time of the newest evidence, or `null`.

A subject appears at most once. If a subject has an active finding, its
`checked` entry (when present) MUST be `finding`. A part the sender can't see
SHOULD be listed as `unknown` rather than left out, so readers can say "we
can't see your power board" instead of implying it's fine.

## 3. Finding

| Field | Required | Type | Meaning |
| --- | --- | --- | --- |
| `code` | yes | string | What was observed, from the registry (section 5) |
| `subject` | yes | object | Which part (3.1) |
| `status` | yes | `active`, `cleared`, `unknown` | `unknown`: the rule can't run right now (no data), so the condition might be true |
| `severity` | yes | `info`, `warning`, `critical` | How much it matters to viewers (3.2) |
| `confidence` | no | `measured`, `likely`, `possible` | How sure the sender is. Absent means not stated |
| `since` | yes | date-time | When `status` last changed |
| `as_of` | no | date-time | Newest evidence; MUST NOT be later than `generated` |
| `still_live` | yes | `true`, `false`, `null` | Whether the stream is still reaching the receiver while this holds. `null` means unknown |
| `evidence` | no | array, at most 8 | Numbers behind the verdict (3.3) |
| `recovery` | no | object | What is being done or can be done (3.4) |
| `worsened` | no | integer ≥ 0 | Times this finding got worse since the stream started |
| `summary` | no | string, at most 160 characters | One plain line in the sender's language, for readers without the registry |

### 3.1 Subject

`{ "kind": …, "id": …, "label": … }`

- `kind`: one of the areas in 5.1, or `x_<owner>_<name>`.
- `id`: 1–64 characters, no whitespace; stable for that part while the sender
  runs (for example an interface name such as `wwan1`, or `hdmi`, `program`).
- `label`: optional display name, at most 64 characters. It MAY be something
  the user chose. Senders SHOULD NOT include labels in snapshots that leave the
  local network, because a label can be private (a Wi-Fi network name).

A finding's identity is the triple (`code`, `subject.kind`, `subject.id`). A
snapshot MUST NOT contain two findings with the same identity.

### 3.2 Severity

Severity is judged by what viewers get, not by how the part looks:

- **`info`**: nothing viewers notice. Worth showing, never an alarm.
- **`warning`**: viewers may notice, or there is a real risk that they soon will.
- **`critical`**: viewers have no picture or no sound right now, or the stream
  is about to stop.

Cleared and unknown are not severities; they are values of `status`. A
cleared finding keeps the severity it had.

### 3.3 Evidence

Each entry: `{ "key": …, "value": …, "unit": …, "window_ms": … }`.

- `key`: dotted lowercase, `[a-z][a-z0-9_]*(\.[a-z0-9_]+)+`, registered for the
  code (section 5) or prefixed `x_<owner>.`.
- `value`: a number, a boolean, or a string of at most 64 characters from the
  key's registered values.
- `unit`: as registered for the key (`bit/s`, `ms`, `count`, `dB`, `V`, `A`,
  `W`, `Cel`); absent for strings and booleans.
- `window_ms`: optional, the time window the value covers.

Evidence MUST NOT contain free text, IP addresses, network names, cell or
location identifiers, phone or SIM numbers, device serials, or stream keys.
The same applies to `summary`.

### 3.4 Recovery

`{ "by": …, "action": …, "state": … }`

- `by`: `auto` (the sender handles it), `ask` (it can, after someone confirms),
  `guide` (a person has to do something), `none`.
- `action`: optional action code, same grammar as finding codes, for example
  `capture.restart_source`. v0 registers none; readers show it only if they
  know it.
- `state`: optional `pending`, `running`, `done`, `failed`.

Recovery is read-only. The format carries no commands.

### 3.5 Life of a finding

- A sender SHOULD raise a finding as soon as its rule holds and SHOULD clear it
  only after the healthy state has held for the rule's recovery time (worse at
  once, better after a hold). The thresholds live in the rule, not in the
  format.
- A cleared finding SHOULD stay in snapshots, with `status: "cleared"`, for
  5 minutes after its `since`, and MUST be removed after 10 minutes. A reader
  that reconnects then still sees what just ended.
- If `live.state` is `not_live`, no finding may have `still_live: true`.

## 4. Reader rules

These rules keep a reader from showing a better picture than the truth.

1. **Freshness by the reader's own clock.** On receipt, a reader records its
   own monotonic time. The snapshot is current until that time plus
   `valid_for_ms`. After that, every finding and check from that sender is
   **stale**: shown as unknown, never as fine. Readers MUST NOT compare
   `generated` with their own wall clock to decide freshness.
2. **Replace, don't merge.** Each snapshot replaces the previous one from the
   same `source.id`. A finding missing from a new snapshot has ended (or is no
   longer reported); it was not "missed".
3. **Order.** Within one `boot`, a snapshot whose `seq` is not greater than
   the last accepted one is ignored. A new `boot` is a restart: accept it, and
   note the restart for the timeline. A jump in `seq` by more than one means
   snapshots were missed; nothing needs repairing, because each one is
   complete.
4. **Unknown fields** are ignored (later minor versions add fields).
5. **Unknown values never look better:**
   - unknown `status` value → `unknown`;
   - unknown `severity` value → `warning`;
   - unknown `confidence` → not stated;
   - unknown `live.state` → `unknown`;
   - unknown code → show `summary` if present, otherwise "<severity> on
     <subject>"; never hide it.
6. **Invalid records.** A finding that misses a required field is shown as
   "a problem the reader can't read" at `warning` for its subject (or for the
   sender), never dropped silently. A snapshot that fails as a whole (not
   JSON, wrong `format`, unsupported `v`) is not accepted; the previous one
   goes stale on its own.

## 5. Codes

A code is `<area>.<condition>`, all lowercase, `[a-z0-9_]` in each part. Others'
codes are `x_<owner>.<area>.<condition>`, where `<owner>` is a stable token for
the project or company.

- The **area** says which part of the chain it's about (5.1).
- The **condition** names what was **observed**, not a guessed cause:
  `link.idle_connected`, not `link.starved_by_sender`. A cause, if known, goes
  into evidence.
- A code never changes meaning. A new meaning needs a new code. Retired codes
  stay in the registry with `replaced_by`.

The registry is [`codes/v0.json`](../codes/v0.json). Each entry has: the
code, the version it was added in, allowed subject kinds, default severity and
confidence, evidence keys with units or allowed values, a plain name and a
technical name (English), and how the reference rule detects it.

### 5.1 Areas

`stream`, `capture`, `audio`, `power`, `heat`, `hardware`, `link`,
`transport`, `relay`, `hub`, `upstream`, `platform`.

They follow a live-video chain from the camera to the platform: capture and
audio inputs, power, heat and box hardware, the uplinks (`link`), the bonding
or SRT transport, the relay, the production hub (for example OBS), the uplink
from the hub to the platform, and the platform itself. `stream` is the stream
as a whole.

## 6. Versioning

- `v` is the major version. v0 is a draft: fields can still change between
  v0 drafts, each with a changelog entry and updated fixtures.
- From v1 on: within a major version, changes are additive only. New optional
  fields, new codes, new evidence keys and new enum values are minor changes,
  and the reader rules (section 4) keep older readers safe. A change of
  meaning needs a new code or a new major version.
- The schema, the registry and the fixtures carry the same version. Extension
  fields start with `x_<owner>_`.

## 7. Mappings to other formats

Informative. They let a hub forward findings without inventing its own.

| stream-status | OpenTelemetry log `SeverityNumber` | Nagios exit | IETF alarm (RFC 8632) | A two-state "ok" flag |
| --- | --- | --- | --- | --- |
| `info` | 9 (INFO) | 0 OK | — | ok |
| `warning` | 13 (WARN) | 1 WARNING | `warning` or `minor` | not ok |
| `critical` | 17 (ERROR) | 2 CRITICAL | `major` or `critical` | not ok |
| status `unknown` | severity kept; attribute `status=unknown` | 3 UNKNOWN | `indeterminate` | not ok |
| status `cleared` | event for the transition | 0 OK | `is-cleared` | ok |

- **OpenTelemetry:** one Event per status change, `EventName` = `code`,
  attributes `stream_status.subject.kind`, `stream_status.subject.id`,
  `stream_status.status`, `stream_status.still_live`; resource attributes from
  `source`.
- **CloudEvents:** a snapshot can be the `data` of a CloudEvent with
  `type` `stream-status.snapshot.v0`, `source` `/stream-status/<source.id>`,
  `id` `<source.boot>-<source.seq>`, `time` = `generated`, and
  `datacontenttype` `application/json`.

## 8. Conformance

- A **sender** conforms if every snapshot it publishes passes
  `tools/stream_status.py validate`: the JSON Schema plus the checks the schema
  can't express (unique identities, registered codes and evidence, `checked`
  consistency, cleared retention, `still_live` against `live.state`).
- A **reader** conforms if it gives the expected answers for every case in
  `fixtures/reader/`.

## 9. Prior art

Informative. v0 borrows on purpose:

- **NOALBS** (<https://github.com/NOALBS/nginx-obs-automatic-low-bitrate-switching>,
  docs at <https://docs.noalbs.com>): the open-source scene switcher many IRL
  setups run. Its readers for the common ingest servers' stats (BELABOX cloud,
  SRT Live Server, MediaMTX, NGINX, Nimble and others) are the closest thing
  to a shared status contract in IRL streaming today, and its pushed
  WebSocket stats feed already marks data stale after a timeout. stream-status
  is meant to sit next to it: findings can be derived from the same receiver
  stats, and a stats consumer can read findings alongside them.
- **Prometheus Alertmanager:** identity from labels, re-sending while firing,
  resolution when updates stop.
- **IETF alarm YANG module (RFC 8632)** and ITU-T X.733: an alarm is identified
  by (resource, type), and clearance is separate from severity.
- **Kubernetes conditions:** `True`, `False`, `Unknown`, and the last
  transition time.
- **Nagios plugin API:** OK, WARNING, CRITICAL and UNKNOWN as outcomes, and
  evidence as label, value and unit.
- **AMWA NMOS BCP-008-01/-02:** worse at once, better only after a hold; an
  overall status that is the least healthy part; counting only worsening
  transitions. **NMOS IS-07:** a 5-second heartbeat and a 12-second timeout.
- **OpenTelemetry logs data model** and **CloudEvents 1.0:** the export
  mappings in section 7.
- **OBS Studio's broadcast performance metrics:** frame counters and
  timestamps carried in SEI messages, the model for the in-band form.
